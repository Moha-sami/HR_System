*hasPermission Directive

Structural directive for controlling element visibility based on user permissions.

Usage Patterns

1. Single Permission (String)
2. Any Permission — OR Logic (Array)
3. All Permissions — AND Logic (Object)
4. Any Permission — OR Logic (Explicit Object)
5. With Else Template (Fallback UI)
6. On Any Element / Component

Common Permission Keys

Based on Figma designs (6 permission groups). Keys follow pattern: group.action

Group Permissions
employee add, edit, delete, suspend, admin_access
job add, edit, delete
site add, edit, delete, shifts
points add_transaction, automation, view_transactions
notifications send
rewards add, edit, delete, inventory

Full key format: employee.add, site.shifts, notifications.send

How It Works

  1. JWT token contains role
  2. PermissionService reads role from TokenService.user().role
  3. Calls GET /api/v1/roles/by-name/Facilitator to fetch permissions
  4. Caches role.permissions in signal map; directive reacts via effect()
  5. Directive shows/hides element based on hasPermission() result

Backend Requirement: GET /api/v1/roles/by-name/:name must exist.

API Reference

Input: hasPermission
Type Example Logic
string 'employee.add' Exact match
string[] ['add', 'edit', 'delete'] OR (any)
all: string[] all: ['add', 'edit'] AND (all)
any: string[] any: ['add', 'edit'] OR (any) — explicit
Input: hasPermissionElse
TemplateRef | null — Template to render when permission check fails
PermissionService Methods (Injectable)
Method Returns Description
hasPermission(perm) boolean Check single permission
hasAnyPermission(perms[]) boolean Check if user has any of the permissions (OR)
hasAllPermissions(perms[]) boolean Check if user has all permissions (AND)
refresh() Promise Force reload permissions for current role
clear() void Clear all cached permissions (on logout)
invalidateRole(role) void Remove specific role from cache
